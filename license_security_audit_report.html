已修复项

已修复 H2

X-Forwarded-For 直接信任

修复方案：新增 ClientIpResolver，从右向左遍历 X-Forwarded-For，跳过可信代理 CIDR，取第一个非可信代理的 IP。可信代理 CIDR 默认覆盖 Docker 三网段 + 回环地址，可通过环境变量 PANJIA_TRUSTED_PROXIES 覆盖。

涉及文件：ClientIpResolver.java、ActivateController.java、JwtConfigProperties.java、LicenseBeanConfig.java、application.yml、docker-compose.yml

已修复 H3

幂等缓存集群失效

修复方案：提取 IdempotentStore 接口，LocalIdempotentStore 作为单实例默认实现（@ConditionalOnProperty(matchIfMissing=true)）。集群部署只需实现接口切换 Redis 即可，无需改 ActivateService。

涉及文件：IdempotentStore.java、LocalIdempotentStore.java、IdempotentCacheStartupChecker.java、ActivateService.java、JwtConfigProperties.java

已修复 预存

自调用事务失效

修复方案：用 TransactionTemplate 编程式事务替换 @Transactional 注解。doActivate 改为 private，事务边界显式包裹。

涉及文件：ActivateService.java、LicenseBeanConfig.java

中危风险

中危 M1

CheckService.parseCapabilities 和 JwtIssuer 使用 new ObjectMapper() 而非 Spring 注入 Bean

涉及文件

  • CheckService.java 第 228 行：tools.jackson.databind.ObjectMapper mapper = new tools.jackson.databind.ObjectMapper();
  • JwtIssuer.java 第 51 行：private final ObjectMapper objectMapper = new ObjectMapper();

问题

ActivateService 已经修复为注入 Spring 的 ObjectMapper Bean（含 JavaTimeModule），但 CheckService.parseCapabilities 和 JwtIssuer 仍然 new ObjectMapper()。当前不涉及 OffsetDateTime 序列化所以不会崩，但有两个隐患：

  • JwtIssuer.parseClaims 第 146 行用 objectMapper.convertValue() 解析 capabilities claim，如果 capabilities 中含复杂嵌套对象（虽然当前是 List<String>），未注册模块的行为可能与 Spring 序列化行为不一致
  • 违反"统一 ObjectMapper 实例"最佳实践，未来扩展时容易遗漏

影响

当前不崩溃，但行为不一致，且未来如果 capabilities 变成更复杂结构（含日期时间），会出问题。

建议

将 CheckService 和 JwtIssuer 中的 new ObjectMapper() 替换为注入 Spring 的 ObjectMapper Bean，与 ActivateService 和 HeartbeatService 保持一致。

中危 M2

SSL Pinning 指纹从配置文件读取，而非硬编码

涉及文件

  • LicenseProperties.java 第 89-92 行：SslPinning 内部类，primaryFingerprint 作为 @ConfigurationProperties 字段暴露
  • PinnedTrustManager.java（未读但设计文档提到）：从 properties 读取指纹

问题

LicenseProperties.SslPinning 将 SSL 证书指纹作为可配置项暴露。攻击者如果能修改 application.yml 或环境变量，可以替换为自己的证书指纹，中间人代理就能解密 HTTPS 流量。

1 攻击者获取客户机器文件系统访问权
2 修改 application.yml 中 panjia.license.ssl-pinning.primary-fingerprint 为自己的中间人证书指纹
3 在中间人代理上拦截 HTTPS 请求，客户端不会报错（指纹匹配）
4 捕获 JWT、authCode、fingerprintHash 等全部敏感数据

缓解因素

  • 设计文档 §3.2 注释"从配置读取"——这是有意为之的设计决策，而非疏忽
  • 攻击者需要已有文件系统访问权，这已经是较高的攻击门槛
  • 完整性自检（IntegrityChecker）会检测 class 文件篡改，但不覆盖 yml 配置

建议

短期：保持现状（设计有意为之）。长期：将指纹改为硬编码到 class 常量（经 ProGuard 混淆），与 LicenseMode.DEV 一样作为编译时常量，运行时不可覆盖。

中危 M3

完整性校验 checksums 与 class 同在 JAR 内，可被同时替换

涉及文件

  • IntegrityChecker.java 第 60 行：EMBEDDED_CHECKSUMS = "META-INF/panjia-checksums.txt"
  • IntegrityChecker.loadChecksums()：优先从 classpath 读取内嵌资源

问题

SHA-256 校验和文件 panjia-checksums.txt 打包在 JAR 的 META-INF/ 下。攻击者如果替换 class 字节码，只需同时重新计算 hash 并更新 panjia-checksums.txt，重新打包 JAR 即可绕过。

缓解因素

  • IntegrityChecker 的注释明确承认了这一点："不防：整体替换 JAR + 伪造内嵌 checksums"
  • 设计意图是"提高门槛"而非"绝对防护"——攻击者需要逆向打包过程
  • 外部 panjia-checksums 文件作为降级方案，首次部署时生成，可由运维锁权限
  • ProGuard 混淆进一步增加了逆向难度

建议

短期：保持现状（设计有意为之的防御层级）。长期：将校验和签名后存储到服务端，客户端启动时从服务端拉取校验和（签名验证），而非从 JAR 内读取。

低危风险

低危 L1

密钥版本号硬编码为 1

涉及文件

  • JwtIssuer.java 第 49 行：private int currentKeyVersion = 1;
  • LicenseProperties（客户端）：无 keyVersion 配置

问题

密钥版本号硬编码为 1，没有密钥轮换机制。如果私钥泄露，需要轮换密钥对，但当前架构无法平滑轮换——所有已签发的 JWT 的 keyVersion=1，客户端只持有版本 1 的公钥。

缓解因素

  • 私钥仅存在于服务端 JKS，不入 JAR、不入 Git、不出进程
  • 即使泄露，可以通过更新客户端 JAR 替换公钥（虽然需要所有客户升级）
  • 设计文档 §1.3 明确"极简原则"，密钥轮换属于大团队才需要的机制

建议

保持现状。如果未来需要轮换，可以在 license-public-key.pem 中放多个公钥，客户端按 keyVersion 选择。当前单密钥足够。

低危 L2

CheckService 未显式校验 JWT exp

涉及文件

  • CheckService.java 第 67 行：claims = signatureEngine.verifyAndParse(jwtToken);
  • JwtVerifier.verify()：调用 .clockSkewSeconds(config.getClockSkewSeconds())

问题

JwtVerifier 使用 jjwt 的 clockSkewSeconds 做 exp 校验，但 CheckService 没有显式检查 claims.getExpiresAt()。jjwt 在 parseSignedClaims 时会自动检查 exp，如果过期会抛 JwtException，所以实际是安全的。但这依赖 jjwt 库的隐式行为，不如 HeartbeatService 中显式检查 claims.getExpiresAt() 那样清晰。

缓解因素

  • jjwt parseSignedClaims 内置 exp 校验，过期 token 会被拒绝
  • CheckService 第二步查数据库 authCode.getEndDate() 做了业务层过期校验
  • 客户端 LicenseServiceImpl.isTokenExpired() 做了本地过期检查

建议

保持现状。jjwt 隐式校验已足够，业务层也有兜底。

低危 L3

devToken 和 authCode 写在 application.yml 中

涉及文件

  • LicenseProperties.java：devToken 和 authCode 作为 @ConfigurationProperties 字段
  • 客户端 application.yml：可配置 panjia.license.dev-token 和 panjia.license.auth-code

问题

devToken 是开发环境预置 token，生产环境应为空。authCode 是首次部署时使用的授权码。两者都通过配置文件传入，如果生产环境 application.yml 中残留了 devToken，会绕过整个授权体系。

缓解因素

  • LicenseMode.DEV 是编译时常量，生产构建（-P prod）时 dev 分支被编译器消除
  • LicenseStartupValidator 在生产模式下强制校验 token 有效性
  • ProGuard 混淆后 LicenseMode.DEV=false 不可被运行时修改
  • HeartbeatScheduler 如果在生产环境检测到 LicenseMode.DEV=true 会大声告警

建议

保持现状。编译时常量 LicenseMode.DEV 是核心防御，配置文件只是辅助。

低危 L4

RestrictedMode 偏移量算法可被逆向

涉及文件

  • RestrictedMode.java 第 77-88 行：computeDeterministicOffset()

问题

受限模式的算薪偏移量基于指纹哈希和授权码的 FNV-1a 哈希取模。攻击者反编译 JAR 后可以看到算法，通过多次比对结果可以反推偏移量并修正。

缓解因素

  • 设计文档 §5.1 明确"错得明显"而非"完全锁死"——目的是让客户不敢用破解版发工资
  • ProGuard 混淆增加逆向难度
  • 偏移量是确定性的，但攻击者需要知道 authCode 和 fingerprintHash 才能计算
  • 即使修正了偏移量，心跳/Check 接口仍会返回 RESTRICT，服务端有记录

建议

保持现状。受限模式的设计意图是"提高破解成本"而非"绝对防护"。

总结

当前授权体系没有高危安全风险。所有剩余风险要么是设计有意为之的边界（M2、M3、L1、L4 有注释明确承认），要么是低风险的一致性问题（M1、L2、L3 有多重兜底机制）。核心密码学机制（RS256 签名/验签、指纹绑定、黑名单、多实例检测、单调时钟、完整性自检）均正确实现且服务端/客户端对齐。
