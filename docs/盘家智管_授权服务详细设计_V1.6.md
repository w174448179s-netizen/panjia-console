# 盘家智管 panjia-console 授权服务详细设计

> 版本：**V1.6（实现修正版）**
> 状态：**设计冻结（可拆任务、AI 按任务生成代码）**
> 工程身份：**独立 Spring Boot 应用（panjia-console）**，与 panjia-app 同 Git 仓库平级
> 部署：我方服务器单机（2C4G/5M）；客户机器仅部署 panjia-app + 业务库（单库）
> 对齐基线：客户端详设 **V1.1**、本服务 V1.6、架构设计 **V2.8**
> 设计原则：**一个人用，不做过度设计；先合并、后好拆**
>
> **V1.6 变更（相对 V1.5）**：
> 1. **工程结构修正**：模块目录名简化为 `common/`、`license/`、`customer/`（启动模块），Maven artifactId 保持 `panjia-console-*` 命名；
> 2. **Spring Boot 4.x 实际适配**：starter 坐标细粒度化（`spring-boot-starter-webmvc`/`spring-boot-starter-aspectj`/`spring-boot-starter-json`），需显式声明 Jackson、Validation、JDBC 依赖；
> 3. **MyBatis-Plus 坐标修正**：实际使用 `mybatis-plus-spring-boot4-starter`（带 `boot4` 后缀）+ `mybatis-plus-jsqlparser`，移除未使用的 MyBatis-Plus-Join；
> 4. **API 路由修正**：管理面从 `/api/panjia/*` 改为 `/api/v1/*`，鉴权面保持 `/api/auth/*`；
> 5. **鉴权面接口契约对齐客户端**：activate/heartbeat/check 的请求/响应字段与 panjia-server 客户端完全对齐；
> 6. **JWT claims 修正**：`offlineExpireAt` 使用 `Date` 类型（JWT NumericDate），不用字符串；
> 7. **PostgreSQL 配置修正**：数据库名 `postgres`，用户 `root/root`，容器名 `postgres`；
> 8. **新增 JsonbTypeHandler**：自定义 PostgreSQL jsonb 类型处理器；
> 9. **新增 JacksonConfig**：显式声明 ObjectMapper Bean（Spring Boot 4 starter-json 为 runtime scope）；
> 10. **编译参数**：`maven-compiler-plugin` 需加 `<parameters>true</parameters>`（Spring Boot 4 不再默认开启）。

## 一、概述

### 1.1 定位

**盘家智管授权服务（panjia-console）** 是我方服务器上的**唯一后端服务**，在一个 Spring Boot 进程内同时承担两件原本拆开的事：

| 模块（Java 包） | 角色 | 对应架构文档 |
|---|---|---|
| `com.panjia.console.customer` | **运营操作台 + 看板**（管理界面、授权决策、告警展示、升级备份） | panjia-console 最小运营后台 |
| `com.panjia.console.license` | **授权引擎**（JWT 签发/验签、指纹绑定、心跳记录、告警产出、状态机） | panjia-console 鉴权核心 |

**一句话**：customer = 操作台，license = 引擎；同进程内通过 **Java 方法调用**协作，不走 HTTP。

### 1.2 合并动机（重要）

原设计把 customer 与 license-server 拆成两个服务、用 localhost HTTP 通信。对单人运维、授权量 < 500 的场景，这属于过度设计：

- 私钥反正只在一台机器上，拆两个进程不会更安全（安全性取决于私钥文件权限，与进程数无关）；
- 跨服务调用要处理鉴权、超时、重试，单机内毫无意义；
- 部署、排查、升级都多一份负担。

**所以合并成一个应用。** 但为保留"将来好拆"的能力，**严格按包边界划分**，模块间只允许通过 `LicenseEngine` 接口交互——将来若真要拆，把 license 模块抽出去加 Controller 即可，业务逻辑不改。

### 1.3 极简原则

> 面向 **单人运营、单机部署、授权量 < 500**。大团队/高并发才需要的机制一律不做。

| 不做（删掉） | 理由 |
|---|---|
| ❌ 拆两个服务 + 内部 HTTP API | 同机单机，方法调用即可，拆了反而多鉴权/超时/重试 |
| ❌ 运营登录 / 账号体系 / session / RBAC | **就一个人用**，账号体系纯属多余点击；可信访问靠 VPN + IP 白名单（见 §6） |
| ❌ 敏感操作二次确认弹窗 | 操作者只有你，弹窗只是噪音；靠操作日志可追溯即可 |
| ❌ mTLS / HMAC / Redis 限流 | 单机内网可信，PostgreSQL 直扛 |
| ❌ 部分唯一索引 / CHECK 约束 | 普通 UNIQUE 即可（两处并发必需的 partial index 除外） |
| ❌ 心跳异步队列 | 同步写库，量太小 |
| ❌ customer 接收心跳 | 心跳由客户端直连 license 模块，customer 只读快照做看板 |
| ❌ JWT 细分错误码 / 多级校验 | 简单枚举，需要时再加 |
| ❌ MyBatis-Plus-Join | 项目未使用连表查询，移除该依赖 |

**关于 Redis 的明确说明**：架构文档 V2.8 中提到的 Redis 属于 **panjia-app（业务主应用）** 的技术栈，授权服务 **不引入 Redis**。防重放与限流由「Nginx `limit_req` + 数据库幂等 + 单机内网可信」承担，见 §6.2。

**保留的最小安全底线**（授权体系地基）：

- ✅ **管理面无应用层认证**：所有管理 API 假定"能访问即可信"，防护完全由网络层（VPN / WireGuard / IP 白名单）承担（§6）；
- ✅ **操作审计日志**（`pj_ops_log`）：记录谁（固定 operator）+ 做了什么，用于事后追溯，不承担访问控制；
- ✅ **整个系统只有一对 RSA 密钥**，私钥存 license 模块的 jks（权限 600），**永远不出进程**；
- ✅ 客户端内置公钥（方案 A），所有客户共用同一公钥验签；
- ✅ 鉴权面（激活/心跳/check）对外 443；管理页面仅内网/VPN，公网不可达。

### 1.4 密钥模型（★ 关键，务必理解）

**整个系统 = 一对密钥（1 个私钥 + 1 个公钥），不是"每客户一把"。**

| 问题 | 答案 |
|---|---|
| 有多少家公司/订阅？ | 任意多家，都用 **同一把私钥** 签发 |
| 不同客户怎么区分？ | JWT payload 里的 `customerNo` / `plan` / `exp` / `fpHash`，与密钥无关 |
| 客户拿到公钥会不会伪造？ | 不能。公钥只能验签，**签不出合法 JWT**（无私钥） |
| 客户篡改 JWT 里的 customerNo？ | 签名对不上，客户端验签直接拒绝 |
| 私钥放哪？ | license 模块的 `panjia-license.jks`，仅本进程加载 |
| 公钥怎么给客户端？ | 构建时内嵌进客户端 JAR（方案 A，首次即已确定） |

> **安全不靠"密钥区分客户"，靠"私钥不泄露 + JWT 内容绑定客户身份 + 客户端逐项校验"。**

## 二、总体架构

### 2.1 部署形态（对齐架构 §10.3）

```
┌──────────────────────────────────────────────────────────────┐
│  客户机器（每客户一套）                                        │
│   panjia-app (Docker Compose 单节点)                          │
│     ├─ 业务模块 + panjia-license-client                       │
│     └─ 本地 PostgreSQL（业务库，仅一个库）                     │
│            ▲ 仅出站 HTTPS :443，无入站、无 DB 连接             │
└────────────┼──────────────────────────────────────────────────┘
             │ 443 (HTTPS)
             ▼
┌──────────────────────────────────────────────────────────────┐
│  我方服务器（单机，2C4G/5M，内网/VPN 运维）                    │
│                                                              │
│  Nginx（:443 反向代理）                                       │
│     /api/auth/*   →  localhost:8081（鉴权面，公网）            │
│     /api/v1/*     →  localhost:8081（管理后台 API，内网）      │
│     静态资源        →  前端 Vue3 构建产物                      │
│                                                              │
│  一个 Spring Boot 进程（panjia-console :8081）                │
│     ├─ customer.*  ← 运营 UI + 授权决策 + 看板                │
│     ├─ license.*   ← JWT 签发/验签、指纹、心跳、状态机        │
│     ├─ jks：panjia-license.jks（私钥，权限 600）               │
│     └─ 两模块通过 LicenseEngine 接口方法调用（不跨网络）        │
│                        │                                       │
│                        ▼                                       │
│  PostgreSQL 16 单实例（:5432，单库）                          │
│     └─ postgres                                               │
│           ├─ schema: auth      （license 模块独占写）          │
│           └─ schema: customer  （customer 模块独占写）         │
└──────────────────────────────────────────────────────────────┘
```

**要点**：

1. 客户机器只有业务库；授权库/内控库只在我方服务器；
2. **单进程单端口**，`customer` 与 `license` 在同一 JVM 内协作；
3. Nginx 只做端口统一 + 静态资源 + 来源限制；路由按 URL 前缀区分（§5.1）；
4. **私钥不出进程**，只有 license 模块加载 jks；
5. **无 Redis 依赖**，所有状态由 PostgreSQL 承载。

### 2.2 技术栈（V1.6，与架构 V2.8 完全一致）

> **设计铁律：全仓一套技术栈，不搞两套。**

| 前端 | Vue3 + Element Plus 2.8.0 | 管理界面 | — |

**Spring Boot 4 适配要点（★ 必读）**：

1. **Starter 细粒度化**：Boot 4 不再有聚合型 `spring-boot-starter-web`，拆为 `starter-webmvc`、`starter-aspectj`、`starter-json`、`starter-validation` 等独立 starter；
2. **Jackson 不自动注入**：`starter-webmvc` 不再包含 Jackson 自动配置，需显式声明 `starter-json` + `jackson-databind`（compile scope），否则 `ObjectMapper` Bean 找不到；
3. **Flyway 需 JDBC**：`FlywayAutoConfiguration` 依赖 `spring-boot-starter-jdbc` 触发 DataSource 自动配置，仅靠 MyBatis-Plus starter 不够；
4. **MyBatis-Plus boot4 后缀**：使用 `mybatis-plus-spring-boot4-starter`（不是 `mybatis-plus-spring-boot-starter`，也不是 V1.5 文档说的"不带后缀"）；
5. **编译参数**：`maven-compiler-plugin` 必须加 `<parameters>true</parameters>`，否则 Spring Boot 4 无法通过反射获取 `@RequestParam` 参数名；
6. **jakarta.\* 命名空间**：代码 import 用 `jakarta.servlet`、`jakarta.validation`。

## 三、数据模型

单库 `postgres`，两 schema 隔离：`auth`（license 独占写）、`customer`（customer 独占写）。

### 3.1 规约

- 全部 `timestamptz`；主键 `BIGSERIAL`；JSON 用 `jsonb`；
- Flyway：`V200001__customer__core_tables.sql`（customer 模块迁移脚本）；
- 所有表加 `created_at`、`updated_at`；
- **不用 CHECK 约束**；保留两处并发必需的 partial unique index。

### 3.2 PostgreSQL 配置

| 配置项 | 开发环境 | 生产环境 |
|--------|---------|---------|
| 数据库名 | `postgres` | `postgres` |
| 用户名 | `root` | `root` |
| 密码 | `root` | 环境变量注入 |
| 容器名 | `postgres` | `postgres` |
| JDBC URL | `jdbc:postgresql://localhost:5432/postgres?TimeZone=Asia/Shanghai` | 同左 |

### 3.3 jsonb 类型处理

PostgreSQL 的 `jsonb` 列不接受 `varchar` 参数，需要自定义 TypeHandler：

```java
@MappedTypes(String.class)
@MappedJdbcTypes(JdbcType.OTHER)
public class JsonbTypeHandler extends BaseTypeHandler<String> {
    @Override
    public void setNonNullParameter(PreparedStatement ps, int i, String parameter, JdbcType jdbcType) throws SQLException {
        if (parameter == null || parameter.isBlank()) {
            ps.setNull(i, java.sql.Types.OTHER);
            return;
        }
        PGobject pgObject = new PGobject();
        pgObject.setType("jsonb");
        pgObject.setValue(parameter);
        ps.setObject(i, pgObject);
    }
    // ... getNullableResult 方法
}
```

使用方式：在实体类的 jsonb 字段上加 `@TableField(typeHandler = JsonbTypeHandler.class)`。

涉及字段：`capabilities`（AuthCode、AuthIssueRecord、LicenseContent）、`detail`（AlertRecord、CustomerAlert）、`params`（OpsLog）、`raw`（HeartbeatRecord）。

## 四、核心流程

### 4.1 签发授权（幂等）

- 管理面 `LicenseMgmtController.issue(CreateLicenseRequest)` → `LicenseEngine#createLicense`；
- **幂等键**：`requestId`（UUID，前端生成），同一 `requestId` 重复调用返回同一 `authCode`；
- 事务内：插入 `t_auth_code` + 写入 `customer.pj_auth_issue_record`；
- 前端调用 `POST /api/v1/license-mgmt/issue`。

### 4.2 激活（JWT 签发唯一时机）

**锁顺序固定**（防死锁）：

1. `SELECT ... FOR UPDATE` 锁 `t_auth_code`；
2. 锁 `t_fingerprint_binding`；
3. 事务外签发 JWT（RS256）。

**指纹绑定规则**：

- 首激活：绑定 `fpHash`，状态 `ACTIVE`；
- 换机：先 `INVALIDATE` 旧绑定，再绑新；
- 多实例检测：同一 `authCode` 短时间出现多个 `fpHash` → 触发 `MULTI_INSTANCE` 告警。

### 4.3 心跳

- 客户端每 24 小时上报 `/api/auth/heartbeat`；
- `HeartbeatService` 同步写 `t_heartbeat_record`；
- **心跳不刷新 JWT**（JWT 过期由 `exp` 决定，离线宽限期由客户端本地计时）；
- 连续缺失 → 告警。

### 4.4 JWT 校验（check）

- 客户端关键操作前调 `/api/auth/check`；
- **双重判定**：`status`（auth_code）+ `t_blacklist`（存在即拒绝）；
- 任一不满足 → 返回 `clientMode=RESTRICT`，**永不 401/403**（见 §5.7）。

### 4.5 吊销 / 恢复 / 换机

- 吊销：`status=REVOKED` + 插入 `t_blacklist`（reason=REVOKE）；
- 恢复：清除 `t_blacklist`，`status` 回 `ACTIVE`；
- 换机：`status=REBINDING`；`cancelRebind` 取消进行中的换机。

## 六、安全设计

### 6.0 管理面网络层防护

**强制规则**：

1. `/api/v1/*` 仅监听内网/VPN，公网不可达；

| 机制 | 实现 | 说明 |

## 七、状态机与定时任务

### 7.1 授权状态机

```
ACTIVE ──(到期)──▶ EXPIRED
ACTIVE ──(换机中)──▶ REBINDING ──(完成)──▶ ACTIVE
ACTIVE ──(吊销)──▶ REVOKED
```

四值：`ACTIVE` / `REBINDING` / `EXPIRED` / `REVOKED`，**无临时态**。

### 7.2 定时任务汇总（Spring `@Scheduled`，单机）

## 八、JWT claims 约定

### 8.1 JWT 签发（`JwtIssuer.issueToken`）

| claim | Java 类型 | JWT 序列化格式 | 说明 |
|---|---|---|---|
| `authCode` | String | 字符串 | 授权码 |
| `customerNo` | String | 字符串 | 客户编号 |
| `fpHash` | String | 字符串 | 指纹哈希 |
| `maxStores` | Integer | 数字 | 最大门店数 |
| `maxUsers` | Integer | 数字 | 最大用户数 |
| `capabilities` | List\<String\> | JSON 数组 | 能力位列表 |
| `startDate` | LocalDate | 字符串（`yyyy-MM-dd`） | 授权开始日期 |
| `endDate` | LocalDate | 字符串（`yyyy-MM-dd`） | 授权结束日期 |
| `clientMode` | String | 字符串 | 客户端模式 |
| `offlineExpireAt` | **Date** | **JWT NumericDate**（epoch 秒） | 离线宽限期截止 |
| `iat` | Date | JWT NumericDate | 签发时间 |
| `exp` | Date | JWT NumericDate | 过期时间 |

> ★ **`offlineExpireAt` 必须用 `Date` 类型**（`Date.from(OffsetDateTime.toInstant())`），不能用 `.toString()`。jjwt 会自动序列化为标准 JWT NumericDate，客户端用 `claims.get("offlineExpireAt", Date.class)` 解析。如果用字符串，客户端 jjwt 无法解析带纳秒的 ISO-8601。

### 8.2 Jackson 配置

Spring Boot 4 需要显式声明 `ObjectMapper` Bean（`JacksonConfig`）：

- 注册 `JavaTimeModule`；
- 禁用 `WRITE_DATES_AS_TIMESTAMPS`；
- `LocalDate` 格式 `yyyy-MM-dd`；
- `LocalDateTime` 格式 `yyyy-MM-dd HH:mm:ss`；
- `OffsetDateTime` 使用默认 ISO-8601 序列化。
